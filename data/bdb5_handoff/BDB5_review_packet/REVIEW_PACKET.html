# BDB-5 R1/R2/R3 Independent Review Handoff

**Date:** 2026-11-10

**Status:** `AWAITING_TWO_REAL_REVIEWERS — R1_R2_R3_EXPLORATORY — NOT_APPROVED`

## 1. Why this handoff exists

The code can record a two-reviewer approval, but it cannot make a reviewer
independent. No approval record has been created for R1, R2 or R3, and none will
be created with invented identities.

Two real people must each:

1. read the model-visible packet and evaluator manifest;
2. confirm the boundary and evidence checks below;
3. provide a reviewer ID, an independence attestation and a conflict-free
   attestation.

The reviewer IDs may be pseudonymous, but they must identify the actual people
who performed the review. They must not be the agent or a fabricated name.

## 3. Reviewer checklist

For each case, review only:

- `model_visible_packet` in the prepared JSON;
- `evaluator_only.manifest` in the prepared JSON;
- the pinned source or CI evidence named by the packet.

Confirm:

- [ ] The case ID in the packet and manifest matches the case being reviewed.
- [ ] The packet contains no gold patch, fix commit, hidden test name, expected
      answer, rubric, label or evaluator-only field.
- [ ] The packet contains no host path, temporary directory or local username.
- [ ] The manifest marks the case `PREPARED`, not synthetic and not approved.
- [ ] The evidence is sufficient to investigate the stated task without the
      evaluator truth.
- [ ] For R1, the source frame and pinned revision are present and consistent.
- [ ] For R2, the packet correctly exposes only the CI/test-harness evidence and
      does not include application source as a claimed cause.
- [ ] For R3, the Django issue and pinned `django/http/response.py` source are
      present and consistent.
- [ ] Running the read-only review reports `REVIEW_PASSED` with no issues.
- [ ] The exploratory R2 result in section 7 was not treated as approval
      evidence and was not scored before approval.
- [ ] The reviewer has no conflict of interest with the case, its labels or this
      evaluation.

If any item fails, do not approve that case. Record the issue instead.

## 4. Recording the sign-offs

Each case needs exactly two distinct reviewers: one `PRIMARY` and one
`SECONDARY`. The CLI assigns the first `--reviewer` as `PRIMARY` and the second
as `SECONDARY`.

Use reviewer IDs and an attestation that the reviewers themselves approve. For
example, the attestation may say:

> I independently reviewed the R1 packet and manifest against the checklist,
> found no label leakage or boundary violation, and have no conflict of interest.

The same attestation text is copied into both sign-offs by the current CLI, so
it must be acceptable to both reviewers. Record each case separately:

```bash
python scripts/bdb5_record_approval.py \
  --prepared "data/bdb5_handoff/bdb5_r1_prepared.json" \
  --reviewer "<REVIEWER_A_ID>" \
  --reviewer "<REVIEWER_B_ID>" \
  --attestation "<REVIEWER_A_AND_B_ATTESTATION>" \
  --attest-independent \
  --attest-conflict-free
```

The recorder defaults to `%TEMP%\bdb5_approvals\`. For this handoff, pass
`--output "data/bdb5_handoff/approvals/BDB5-R1-approval.json"` (or the matching
case) so the record stays with the package. Approval files are not committed.
The command prints `APPROVAL_RECORDED` and the approval hash.

An approval is bound to the packet hash, manifest hash and label-vault hash. If
any of those change, the approval is rejected as stale.

## 5. What approval does and does not establish

Approval establishes that two named people attested to the boundary review. It
does not:

- score a model result;
- establish that a model is correct;
- convert the exploratory R2 output into a benchmark result;
- unblock T1 or P1.

After approval, a result can be scored with:

```bash
python scripts/bdb5_score_prepared.py \
  --prepared "data/bdb5_handoff/bdb5_r2_prepared.json" \
  --result "<RESULT_JSON>" \
  --approval "<APPROVAL_JSON>"
```

The scorer makes no provider call and emits
`REAL_CASE_SCORE_NOT_BENCHMARK_RESULT`.

# How to approve — plain English

You do **not** need to code. I can run every command. Approval only needs two
real people to read the review packet and confirm it is clean.

## What approval means

Approval means two people checked that the task given to the AI does not
accidentally contain the answer, the fix, a hidden test, a label, or a local
file path.

It is a review of the **packet**, not a vote on whether the AI was right.

## What you need

- About 10–15 minutes per person.
- Two real people. You can be one of them.
- The second person can be a friend, coworker, or classmate.
- No coding and no model run.

The same two people can review all three cases: R1, R2 and R3.

## Step 1 — Pick two people

- Reviewer A: you, if you are willing to read the checklist.
- Reviewer B: one other real person.

Use a name or nickname for each reviewer ID. The ID must identify the actual
person who did the review; it can be pseudonymous.

Do not use me as a reviewer. Do not use two names for the same person. Do not
give me names of people who did not actually read the packet.

If you cannot find a second real person, the cases stay unapproved. That is the
honest outcome; I will not invent a reviewer.

## Step 2 — Both people read the review handoff

Open this file:

`data/bdb5_handoff/REVIEW_HANDOFF.md`

Read sections 1–3. For each case, confirm:

- [ ] The case ID is correct: R1, R2 or R3.
- [ ] The model-visible packet does not contain the answer, the fix commit, a
      hidden test name, a label, a rubric, or an expected answer.
- [ ] The packet does not contain a local username, a Windows path, or a
      temporary folder path.
- [ ] The evidence is enough to investigate the task without the answer key.
- [ ] R1 has a source frame and pinned revision.
- [ ] R2 shows only CI/test-harness evidence and does not claim an application
      source cause.
- [ ] R3 has the Django issue and the pinned `django/http/response.py` source.
- [ ] The reviewer has no conflict of interest with the case or its labels.
- [ ] The exploratory R2 result was not used as approval evidence and was not
      scored before approval.

If everything passes, the reviewer says **PASS** for that case. If anything
fails, the reviewer says **FAIL** and names the case and the problem.

You do not have to run the Python commands. I can run the automated boundary
check after you tell me the human review is done.

## Step 3 — Each person replies

Ask each reviewer to send a short reply like:

> I reviewed R1, R2 and R3 independently. I found no label leakage, answer
> leakage, hidden test, local path, or other boundary problem. I have no
> conflict of interest.

They can also reply per case:

> R1: PASS. R2: PASS. R3: PASS. Reviewed independently; no conflict.

If a reviewer says FAIL, stop. Do not record approval for that case.

## Step 4 — Agree on one sentence

The recorder copies one sentence into both sign-offs. Both reviewers must agree
to the exact sentence before I record it.

Example:

> We independently reviewed the R1, R2 and R3 packets, found no label leakage or
> boundary violation, and have no conflict of interest.

Both people must approve that wording. Do not write it for someone who has not
agreed to it.

## Step 5 — Send me four things

Send me:

1. Reviewer A ID:
2. Reviewer B ID:
3. The exact agreed sentence:
4. Confirmation that both people actually read the packet and said PASS.

That is all I need. I will run the recorder for R1, R2 and R3 and save the
approval files under:

`data/bdb5_handoff/approvals/`

## Step 6 — What I do next

I will:

- run the approval recorder for each case;
- save `BDB5-R1-approval.json`, `BDB5-R2-approval.json` and
  `BDB5-R3-approval.json`;
- verify the two reviewer IDs, both attestations, and the packet hashes;
- score R1, R2 and R3 only after their approval records exist.

Approval does **not** unblock T1 or P1. Those are separate engineering blockers.
