# Milestone 3B.1 — Docker lifecycle validation

Date: 2026-11-05. **Restricted lifecycle gate: provisionally passed for the tested trusted fixtures and this Docker Desktop environment; not a security certification.** General untrusted execution remains blocked. Cleanup during daemon failure, abrupt host termination and a real external console-cancellation signal was not demonstrated; see limitations below. The tests exercise `KeyboardInterrupt` injected after a real container starts, not delivery of a physical Ctrl+C.

## Changes

`blackbox/repair/execution.py` now requires `BLACKBOX_REPAIR_DOCKER_IMAGE_ID` to be the full, explicitly selected local `sha256:` image ID and uses `docker create --pull never` with a unique random name and matching ownership label. A durable exclusive pending journal stores name, identity and daemon ID before creation. The runner inspects the created container's identity, image, forced `65534:65534` user, network, read-only root, capability drops, no-new-privileges, memory, swap, CPU, PID, tmpfs and mount settings before starting. The in-container bootstrap checks effective UID/GID, effective capabilities, no-new-privileges and seccomp mode before pytest. `/tmp` is limited to 32 MiB; the disposable workspace remains the only bind mount. `auto` no longer falls back silently to process execution. Explicit process mode remains restricted to trusted fixtures.

On success, failure, timeout and handled cancellation, `recover_container()` checks the original Docker daemon and exact name and ownership label, forcibly removes only that matching container if present, and confirms its absence using the daemon. It records lifecycle events in `data/repair-container-audit.jsonl`. Uncertain cleanup leaves the journal and returns `security_blocked`; the pipeline records `SECURITY_BLOCKED`, and later Docker runs fail closed. A create timeout leaves the journal because the daemon request may still be in flight. An operator can inspect the journal and audit and, only after confirming no repair is active and any in-flight create request has settled, run `python -m blackbox.repair.execution --recover` against the original daemon. Never delete the journal to bypass uncertainty. A power loss, daemon outage or SIGKILL prevents immediate cleanup; no code can guarantee cleanup while the daemon is unreachable. Recovery is operator initiated and does not automatically decide whether a live process is abandoned. The journal serializes normal runs; it is a local coordination mechanism, not tamper-proof storage against an administrator.

## Engine, image and live integration tests

Engine: Docker Desktop 29.9.2, WSL2 Linux, cgroup v2. Image `sha256:5c1b730d1ae3e028494c8f6fa48a67a51d5ed2090ab0ec56b79416adb79b4fe4`, local Python 3.12.12 and pytest 8.4.2, derived from base digest in report 30. Setting a local image ID is an explicit operator selection, not independent supply-chain approval; image build dependencies remain without a hash lock.

`tests/test_docker_lifecycle.py` invokes the actual Docker Engine with pinned `argument_validation` source from revision `b96840fef85585904c9348e213dbbec9c0ca521a`. The suite verifies passing and failing tests and cleanup; invalid image; unreachable daemon; simulated removal failure leading to blocked state and explicit recovery; refusal to remove a foreign unlabelled container; inspected settings and non-root bootstrap; and cancellation after a real container starts. Removal failure and cancellation are deliberately injected; they are not real daemon failures or physical keyboard signals. The resource test inspects config; it does not exhaust resources.

The timeout acceptance test uses a trusted pytest hook to delay execution of the actual pinned test for 30 seconds, observes `PINNED_TEST_STARTED`, sets a 3-second timeout, and verifies the journal is cleared and the exact journaled container name is absent. The hook is test harness code; no pinned fixture is edited. A separate isolated integration run passed **8/8** before the final daemon-binding change; the final full-suite run below includes these eight tests. Test-only journals use isolated temporary directories; production runs use the single shared journal.

One concurrent earlier full test run reported 2 false failures because its assertions compared all BLACKBOX containers while the independent live repair was running. The tests were corrected to inspect only their own journaled identities; the subsequent full run passed. This does not imply those two results were product failures.

## Remaining limitations

The Docker engine and host are trusted; labels and local journal are not protection from a privileged adversary. Checks of seccomp mode do not test individual syscalls; network and host secret probes in report 30 are limited; cgroup values do not prove behavior under exhaustion; inherited image content and transitive dependency integrity remain unverified. Abrupt termination, actual Ctrl+C delivery, daemon crashes during creation/removal, Windows host compromise, concurrent operator recovery, and adversarial container escape have not been validated. No arbitrary third-party repositories, deployments or PR automation were enabled. No broad production safety claim is made.

Final full regression: with `BLACKBOX_M3B_TEST_IMAGE` set to the image ID above, `.venv\Scripts\python.exe -m pytest -q` produced **91 passed, 0 failed, 0 skipped, one Starlette/httpx deprecation warning in 53.68 seconds**. Without that explicit variable, the eight Docker integration tests are skipped by design. The full test run includes real engine operations and the pinned delay-hook timeout test.
