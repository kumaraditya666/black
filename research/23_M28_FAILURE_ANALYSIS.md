# Milestone 2.8 pre-change failure analysis

Recorded 2026-11-04 before implementation changes. Sources: EVALUATION.md, data/m27-final-original.json, data/milestone27-live-cases.json, and the pre-change schema, validator, provider and collector.

- The original report attributed line 26 to `main`, while the cited `frame:0` records function `<module>` at line 26; `frame:1` records `main` at line 17. The model had both frames. The validator checked that an ID and a line appeared somewhere, not whether the stated function, line and cited frame agreed. The direct mechanism is unchecked model prose; why the model generated it is unknown.
- The final 2.7 multiple-plausible and unknown-root cases were persisted only with the generic error `Evidence validation failed: output references unsupported evidence or a source line.` The raw model responses and provider usage were deliberately discarded on failure, so their exact invalid references cannot be reconstructed. A prior diagnostic of a different unknown-root run returned `line 1` for an unresolved frame, while validation accepted line numbers only from resolved snippets; this identifies one observed failure mechanism, not the cause of both final failures.
- The earlier missing-evidence diagnostic referenced a `missing_evidence` ID absent from the then-current evidence list; adding a corresponding record led to a valid abstention in another run. This is a schema/evidence-interface mismatch. Subsequent runs still sometimes failed generic validation. Model formatting, evidence design and overly broad reference validation can each contribute; per-case attribution is unavailable without preserved output.
- The original snapshot contained exception type, message, frame ordering, commit, exact source lines and a same-file static caller. It was sufficient to report the recorded frame names and syntactic caller; it did not prove captured runtime argument values independently. Synthetic missing-source cases intentionally lacked source and a resolvable commit.
- The provider requested a 2,048-token context with `truncate=false`, `shift=false`, a 768-token output cap and explicit failure on output-length termination. This makes silent truncation less likely, not proven absent. Token counters for failed 2.7 attempts were discarded, and no raw failure output is stored; therefore context or output-limit causes cannot be ruled in or out. The original completed run has provider token counters in its persisted report.
