# Milestone 4B.2 — oracle context diagnostic

## Preregistration (written before M4B.2 model calls)

**Question.** When the final investigator receives a compact, trusted excerpt selected by the evaluator, does it produce better immediate mechanisms than it does from the fixed snapshot? This is a diagnostic reuse of the eight already exposed 4B.1 cases, not a fresh or held-out generalization benchmark. The 4B.1 registry, labels, results, fixture files and source revision are not changed. Frozen source revision: `76564779c56068107aeccda8205147c6bbbea86e` (`refs/blackbox/m4b1-freeze`).

**Conditions.** For every suitable registered case, run the ordinary `blackbox.investigator.investigate` final investigator twice with the same `qwen3.5:4b` provider, pinned revision, event, final Findings schema, validation and output limits: (A) its recorded initial evidence snapshot; (B) that same snapshot plus one evaluator-selected, exact function body from an approved fixture file. Source bodies will be retrieved by the trusted local dispatcher from the frozen Git object, never from the worktree. For the five retrieval-opportunity cases, the chosen function is the registry's predeclared useful symbol. For the visible, runtime-unknown and negative controls, use the recorded stack function body (this supplies the strongest compact source context without suggesting a hidden answer). Do not include ground-truth labels, expected causes, reproduction tests, or solutions in prompts. No behavioral contract may be added unless it appears in approved source or developer documentation. The source alone is not treated as a specification.

**Scoring.** Preserve ordinary schema and evidence validation. Score primary mechanism correctness separately against the frozen labels; score expected abstention on the runtime-unknown and negative controls; record unsupported causal assertions, outcome, schema/validation success, provider/runtime failures, token usage and latency. A validated abstention on a positive case is not mechanism correctness. A correct statement about local code is not evidence that the code executed. Count every run and error. Same author/scorer and unblinded case reuse will be reported as limitations.

**Range-selection isolation.** Separately exercise the existing `find_symbol` request through the trusted dispatcher on the five predeclared retrieval-opportunity cases. A symbol request carries no line numbers. The backend must return exact definition line/end-line from the immutable approved Git blob; duplicate matches must be explicit ambiguity, missing definitions explicit not-found, and source must pass existing provenance validation. Compare its deterministic outcomes to the 4B.1 trace's invalid range / irrelevant request outcomes. This is interface isolation, not a model accuracy comparison and not a root-cause inference.

**Model-capacity decision.** Only if oracle excerpts do not improve evidence-supported mechanisms or appropriate abstention will we run a separate compact self-contained probe, scoring its structured answer against a separately prepared answer key after calls. Use only locally available and authorized models, same evidence and task; do not download models. Report hardware, input/output tokens, latency and validation. If no second authorized model is available, say so and do not infer capacity from its absence.

**Safety and budget.** Read only regular source blobs at the exact frozen commit and within the registered Python paths. No model tool calls, execution, repairs, network access, Docker actions, or source writes. At most 16 final-model calls (two per each of eight cases), existing output limits and provider timeout; process is bounded by the existing provider timeout. Preserve redaction, fail-closed validation, provenance, fixture approvals and frozen files. The Ollama daemon is outside process cancellation containment; client cancellation may not stop daemon inference. Redaction is best-effort. This diagnostic does not change the reliability gate.

## Existing 4B.1 failure classification (observations and hypotheses)

Observed in `research/48_M4B1_TOOL_USE_FEASIBILITY.md` and `data/m4b1-results.json`: B made three relevant requests out of five useful opportunities. Those requests retrieved the declared `scale`, `choose`, and `final_item` bodies, and each final result was a validated `INSUFFICIENT_EVIDENCE`. The caller case requested an irrelevant range and missed `run`; three controls received unnecessary out-of-range requests; the injected-comment requests were malformed. B completed 4/8 versus A 7/8 and C 8/8. Every completed final diagnosis abstained; six positive cases had zero correct primary mechanisms. No context-limit/deadline error occurred. A and C abstained appropriately on both controls; B failed both. Raw malformed model requests were not retained, so exact bad fields cannot be assigned. The final schema/validator distinguishes malformed output and evidence-reference errors from successful abstention, but results do not show a final validation rejection for the three relevant reads.

Interpretation: incorrect selection is observed for the caller and no-opportunity cases; invalid/missing source ranges and malformed actions are observed request-interface failures where the trace records them, while the raw fields for malformed actions are unavailable. For the three useful reads, retrieval succeeded and final abstention followed; this rules out “no source was fetched” for those instances, but does not establish poor reasoning by itself. The conservative final prompt (`blackbox/investigator.py`, `SYSTEM`) requires event plus resolved frame evidence for a `LIKELY_CAUSE`, says static source does not prove execution, and says an immediate mechanism does not establish upstream cause. The hidden labels specify intended fixture behavior, but many behavioral contracts are not present in incident telemetry or approved developer docs. Therefore prompt conservatism and missing behavioral/runtime evidence are live explanations; model reasoning capacity is not established. Output-schema/validation failures explain some retrieval-arm failures, not the repeated validated abstentions. These distinctions are hypotheses about causes, not measured causal effects.

The five positive retrieval-opportunity cases and the visible positive control abstained in both conditions (0/6 correct primary mechanisms in fixed context; 0/6 with oracle context). Thus oracle excerpts changed **0/6 outcomes**. The runtime-unknown and negative controls abstained appropriately in both conditions (2/2 each). ## Symbol-resolution results

All five preregistered useful symbols resolved uniquely inside their fixture's approved Python paths at the frozen Git revision. A trusted evaluator adapter then used the AST definition's `end_lineno` and the dispatcher's immutable-blob reader to obtain an exact function body; provenance validation succeeded on all five. The model supplied only the function symbol in the resolver request, with no line numbers. This isolates the range-invention problem: the symbol-first path can locate exact spans for these fixtures without model-generated line ranges. It is a deterministic interface check, not a live model-selection comparison; the oracle selection was given by the frozen registry's useful-symbol metadata. None of the five fixtures contains a duplicate target symbol, so duplicate-match behavior was not empirically measured. Existing `find_symbol` reports a `matches` array; consumers must treat multiple matches as ambiguous rather than choose one. Static matches still do not establish execution.

In 4B.1, the revised model made three useful requests, one irrelevant successful range request, three unnecessary/out-of-range control requests, and one malformed request; the raw malformed fields were not retained. The new deterministic symbol-first span resolution removes guessed line numbers from the retrieval request itself, but it cannot repair incorrect symbol selection or supply a missing behavioral contract.

## Capacity probe, resources and security status

**Conditional probe preregistered before its calls.** Because none of the five positive cases improved with oracle context, five compact tasks were sent to the same `qwen3.5:4b`, one per positive fixture. Each contained only the reported exception and exact trusted function body, and requested JSON describing the immediate operation, relating it to the exception, and stating whether execution was established. No expected label, hidden contract, test result, or proposed fix was supplied. All **5/5 outputs were structurally valid** and described the visible local mechanism consistently with source. Four correctly said execution was not established; the config case incorrectly said execution was established, an unsupported claim. The compact probe used **578 input / 302 output tokens** total, with 1.18–1.64 second latency per call. It shows the model can interpret these compact code snippets under a direct task prompt; it does not establish general debugging capacity or intended contracts.

Before the probe: Windows; Python 3.14; Intel i7-13645HX (14 cores); 16,478,072 KB visible RAM with 3,959,068 KB free; Intel UHD Graphics and NVIDIA RTX 4050 Laptop GPU (reported 4,293,917,872 bytes adapter RAM). Ollama has `qwen3.5:4b` (3.3 GB), `qwen3.5:9b-q4_K_M` (6.6 GB), and `qwen3:4b` (2.5 GB) already installed. Only the already evaluated 4B model was used. The 9B model's installed size exceeds currently free system memory and reported GPU memory, so it was not loaded. No model download or larger-model superiority claim.

## Bottleneck assessment

Evidence best supports **B. final prompt / evidence presentation** and **D. missing runtime or behavioral evidence**, with an interface range-selection contribution in 4B.1. Oracle context did not help the existing investigator, but the compact probe interpreted the same source mechanisms in all five tasks. The ordinary final prompt explicitly says an immediate mechanism does not establish upstream origin and instructs abstention when that origin is unsupported; its output was consistently cautious even when a local mechanism was visible. Separately, the hidden config contract is absent from source-only prompts, and no runtime input or branch evidence establishes historical execution. These results weaken a broad “model cannot reason about code” hypothesis; they do not prove the compact probe prompt alone caused the difference, since its output format, task wording, and context length also changed.

**A. Source selection:** contributes to the 4B.1 caller and unnecessary-control failures; not the explanation for the three successful relevant reads, nor for the M4B.2 oracle arm. **B. Source presentation and prompt structure:** supported as a likely contributor by the contrast between uniform final abstention and direct compact interpretation, but not isolated in a matched-prompt ablation. **C. Model reasoning capacity:** not established as dominant; this small probe shows local mechanism interpretation, while one unsupported execution claim demonstrates remaining errors. **D. Missing runtime/behavioral evidence:** directly limits upstream attribution and contract judgments. **E. Schema/validation:** caused some 4B.1 tool-arm failures, but not the M4B.2 outcomes (16/16 final validations and 5/5 compact JSON outputs passed). Multiple causes apply; this is not a definitive causal ranking.

## What this experiment means

An **oracle experiment** gives the system an answer to one intermediate question—in this case, a trusted excerpt selected by the evaluator—to see whether the later reasoning step can use it. “Oracle” describes who selected the context; the excerpt is real source from the frozen fixture, not the hidden expected answer. Tool selection and reasoning are separate: choosing a useful function is one task; interpreting its body and deciding what can be concluded is another. **Symbol resolution** lets a request name `scale`, while trusted code finds the exact definition and line span in the approved commit. This avoids asking the model to guess line numbers; ambiguous matches must remain ambiguous.

An **ablation** removes or adds one component while keeping the rest fixed. Here, A versus B changes only whether the compact trusted excerpt is supplied. An improvement would show that this excerpt helped on these already seen synthetic cases; it would not prove general accuracy. No improvement would still leave prompt structure, missing behavioral contract, runtime uncertainty and model capacity as competing explanations. Source code can show what a function does, but without an approved contract it may not show what it was supposed to do; without runtime data it may not show which input or branch caused the reported event. Before/after scores are descriptive and small: they do not establish statistical significance, causal superiority, real-world reliability, or generalization to new cases.
