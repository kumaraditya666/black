# Milestone 4A — BLACKBOX gap analysis

Date: 2026-11-05. This compares the current working tree, including uncommitted 3B.1–3F work, with documented or public-source features—not with inaccessible Seer internals. [41_M4A_COMPETITOR_ARCHITECTURES.md](41_M4A_COMPETITOR_ARCHITECTURES.md) identifies each external finding's source and confidence. The three experiments are hypotheses, not claims of improvement.

## What BLACKBOX actually does

[`Event`](../blackbox/schemas.py) stores a UUID, time, full Git commit, exception type/message, traceback and client-supplied frames. [`Store.ingest`](../blackbox/store.py) redacts selected patterns and groups events by exception and ordered frame signature; a recorded frame is not independent proof of execution. [`collect`](../blackbox/investigator.py) assembles a fixed snapshot: recorded event/occurrence summary, up to ten resolved frames with nearby lines, bounded same-file caller matches, and 3D's static related-code snippets. The full traceback is persisted but is not passed wholesale to the investigation model. The collector does not expose a trace/span/log query tool or record argument values, causal request IDs or deployment history. Some of those facts may be absent even when an event exists. Redaction is best effort; there is no basis to assume arbitrary application data is safe to send to a provider.

[`retrieve`](../blackbox/repository_intelligence.py) reads from a specified Git revision and returns one-hop syntactic caller/callee candidates in a bounded directory subtree; it is not model-controlled iterative search and does not prove dynamic binding. [`Provider.analyze`](../blackbox/providers.py) makes a structured model request without a tool channel. [`investigate`](../blackbox/investigator.py) checks source integrity and validates output; 3F permits one **format/reference recovery** call in a specific error case, not a hypothesis-testing loop. [`review_hypotheses`](../blackbox/semantic_verification.py) qualifies a small set of claims and checks cited source identity, but does not execute a proposed experiment or prove causal prose. `LIKELY_CAUSE` remains a review-required hypothesis and can coexist with insufficient upstream evidence.

[`evaluate`](../blackbox/repair/eligibility.py) requires a matching evidence/hypothesis approval, trusted registered fixture, exact revision and hashes. [`run_repair`](../blackbox/repair/pipeline.py) runs the predetermined reproduction before generation, validates a patch confined to allowed files, then tests it in a disposable copy and runs regressions. [`execution.py`](../blackbox/repair/execution.py) has a restricted Docker path with an explicit image identity and journaled cleanup; arbitrary repositories remain blocked. The test-derived status is not independent evidence of production safety or diagnosis correctness.

## What the measurements do and do not say

- In [3D](37_M3D_REPOSITORY_INTELLIGENCE.md), adding source context retrieved both targeted excerpts. B passed tests on two patches vs A on one, but attempted cases differed; the window diagnosis was wrong, config failed validation and ambiguity handling worsened. This is not proof that retrieval caused a better repair or worse reasoning.
- In [3E](38_M3E_SEMANTIC_REASONING.md), a prompt arm abstained on the false-report control, but failed validation twice on the ambiguous case. Those failures are not abstentions. All five cases were previously exposed to the author/scorer.
- In [3F](39_M3F_CAUSAL_REASONING.md), newly authored unblinded cases gave identical A/B outcomes and no natural reference retries. A deliberately injected missing-reference fault exercised the recovery path; it was not a natural benchmark success. The same author and scorer mean this was not independent adjudication.
- The frozen small fixtures, constrained prompts and a single machine/model cannot determine whether the bottleneck is context, tool use, inference capability, runtime data or task construction. Missing runtime origin is a fact about particular snapshots; it is not proof that collecting sensitive raw values is safe or necessary.

## Differences worth testing

Seer's documented runtime linkage suggests testing **correlated, minimized observations**; its inaccessible internals do not tell us how to copy its causal reasoning. SWE-agent's ACI suggests testing **small precise read actions and actionable feedback**, not giving BLACKBOX a shell. OpenHands illustrates **durable action/observation records and explicit budgets/confirmation policies**, not a blanket causal verifier. These are transferable design hypotheses derived from [Sentry's telemetry description](https://blog.sentry.io/seer-debug-with-ai-at-every-stage-of-development/), [SWE-agent's ACI](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/docs/background/aci.md) and [OpenHands event architecture](https://docs.openhands.dev/sdk/arch/events).

Priority recommendation: test **A, model-selected read-only evidence retrieval**, first. The 3D window and trim cases show concrete missing source relationships, and this is the smallest experiment that can compare selection against the existing fixed retriever while leaving execution and telemetry scope unchanged. It does not follow that A will improve diagnosis: 3D also shows added context coinciding with incorrect explanations. B and C should be staged separately, not bundled with A.
