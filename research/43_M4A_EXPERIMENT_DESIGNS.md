# Milestone 4A — experiment designs

These are proposals, **not implemented or measured**. They borrow bounded-interface ideas from [SWE-agent's ACI](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/docs/background/aci.md), action/observation provenance from [OpenHands events](https://docs.openhands.dev/sdk/arch/events), and the value of linked runtime evidence described by [Sentry](https://blog.sentry.io/seer-debug-with-ai-at-every-stage-of-development/). None is a reconstruction of Seer's private internals. Estimates below are provisional budgets, **not measured costs**; they may be infeasible for the 2,048-token 4B context and must be feasibility-tested on separate development cases before locking a held-out evaluation.

## Shared evaluation contract

1. **Holdout before implementation tuning.** Seek at least 18 new, locally authored, trusted, immutable tasks: six source-identifiable, six genuinely ambiguous without runtime evidence and six false/misleading/contradictory reports, including multi-file, boundary and changed-revision cases. An independent author should specify expected behavior, causal chain, minimal evidence and allowed observations before seeing candidates. Two independent reviewers blind to arm and model output origin should label/adjudicate; if not available, mark the study **unblinded and exploratory**, never call the labels independent. Split by fixture family and design, not merely random copies of one bug. Preserve the existing 3C/3F cases for development only. Record freeze commit, file hashes, tests, expected facts, tool-visible data and sealed adjudication separately.
2. **Within-case comparison.** Same immutable event and revision, model, decoding settings, approval policy and evidence availability per pair. Counterbalance arm order and repeat each case twice; record each run, seed if applicable, cached/warm state, exact hashes and changes. Do not pool repeated runs as independent bugs. If a tool arm receives an extra model turn, report it and run a budget-matched non-tool control where feasible; if the 4B provider cannot reliably emit a bounded request, count invalid requests rather than switch models silently.
3. **Outcomes.** Blind-score (a) exact immediate mechanism, (b) supported upstream cause vs explicit insufficiency, (c) unsupported/contradicted claims, (d) false certainty on ambiguous/negative cases, (e) valid abstention and missed diagnosable causes, (f) provenance and source revision correctness, (g) malformed, timeout and unavailable outcomes. Count every failure in denominators. Measure tool calls, retrieval precision/recall against frozen labels, input/output tokens, wall time, provider errors and context overflow. Do not score valid citations as causal correctness or passing patch tests as a correct diagnosis.
4. **Safety and privacy.** Only local pinned trusted fixtures; no arbitrary repository, shell, model-generated command, network lookup, PR, merge or deployment. Existing explicit approvals and Docker test isolation stay intact. Read-only tools must validate repository identity and exact commit, reject traversal/symlink escapes, enforce per-call and total bounds, redact, and return provenance/unavailable status. Captured source and telemetry remain untrusted text. External-provider use retains the existing explicit snapshot-consent mechanism; do not send raw secrets. Halt affected runs on provenance or isolation failure. Do not create fixtures or modify tests in response to outcomes.
5. **Decision rule.** Before looking at holdout, lock the exact rubric and thresholds. Proposed minimum for a go decision: all tests and security checks pass; no unverified claim is presented as verified; zero unauthorized writes/execution or wrong-revision reads; at least two paired cases improve a predeclared causal/appropriate-abstention score and no more than one regresses; no new false-certainty case on the six ambiguity/negative controls; report all denominators, paired changes and uncertainty. These deliberately strict, **exploratory** thresholds do not statistically prove a zero error rate. A tie, failure, inaccessible independent labels, too many errors or infeasible context is **inconclusive/reject**, not a success. Publish bounded confidence intervals and raw paired outcomes; do not select the best repeat after seeing data.

## A. Agent-controlled read-only evidence retrieval — recommended first

**Hypothesis.** A model can choose a useful next source excerpt better than the current automatic one-hop selection when relevant code is outside it; it may also chase misleading results. The 3D `rolling_sum` body and `total` caller motivate the question but are tuning examples, not the holdout.

**Engineering change, if later authorized.** In an evaluation-only harness add two typed operations over Git objects: `search_symbols(revision, name, scope)` returns bounded candidate paths/lines; `read_excerpt(revision, path, start, end)` returns exact bounded numbered lines and a provenance ID. A host dispatcher, not the model, validates the pinned repository/commit and allowed path. Allow at most **two** retrieval calls, max **20 lines / 1,200 characters per call**, max **2,000 characters total**, and at most **three model turns** including the final answer. Deduplicate results; return explicit `not_found`, `ambiguous`, `limit`, `unavailable` and redaction notices. Output remains structured hypotheses and insufficiency, not `ROOT_CAUSE_SUPPORTED` without independent evidence. Search results or repository comments never become instructions. No shell, process, editing or network tool is available. Model selection of an excerpt never expands allowed patch files or grants repair approval.

**Control.** Existing 3D fixed retrieval with its actual bounded snapshot and one model response; additionally a budget-matched fixed-order two-read control if resources permit. Same evidence universe and frozen revision. Instrument actual bytes offered and selected, not only number of calls. Do not automatically append full repository content or discard counterevidence to make the tool arm fit.

**Expected benefit / risks.** Could recover a missing caller or callee on unseen cases. Risks: 4B fails tool schema, chooses distractors, omits contradictory evidence, repeats calls, hits context limits or hallucinates a runtime call. A syntactic match can be wrong due to Python binding; label it static. Search may reveal secrets or return adversarial content; deny unsafe paths and use bounded redaction, acknowledging redaction is incomplete. Concurrent data or mutable refs must not affect a pinned run.

**Cost hypothesis.** At most two extra model requests plus two bounded reads, up to roughly 2,000 extra source characters plus schemas and prior context. Token cost and latency are unknown; on a 2,048-token context, even this may require reducing *optional* evidence or returning `EVIDENCE_TOO_LARGE`, never silent evidence loss. Record all tokens and wall time, including cold load. Do not estimate dollars without a provider price and measured usage.

**Accept/reject.** Apply shared decision rule; additionally require deterministic tests for traversal/symlink, commit identity, scope, no writes, rate/call/size cap, secret handling and explicit missing evidence. The trace must show which exact request supplied each relied-on excerpt. Reject if apparent gains require extra withheld information unavailable to control or if the primary result improves only on the old 3C/3F cases.

## B. Bounded hypothesis-testing investigation

**Hypothesis.** Asking for a discriminating observation between at most two competing hypotheses can reduce unsupported causal attribution when that observation already exists in the authorized evidence set.

**Engineering change, if later authorized.** Starting from the same snapshot and typed source reads as A, request at most two structured hypotheses, each with predicted observable evidence and competing explanation. Permit one model-selected query from a fixed enum of existing evidence/source lookups; host returns evidence IDs or `unavailable`. A final structured response must separately mark supported observation, unverified mechanism, upstream hypothesis and missing data; a deterministic evaluator checks only evidence identity/revision and explicit typed predicates, never arbitrary prose entailment. No new execution, shell or self-approved test is allowed. Keep a compact append-only record of hypothesis → requested evidence → result → retained/qualified/abstained; contradictory or unavailable evidence cannot be replaced by a model assertion.

**Control.** The A evidence interface with the same max turns, source bytes and tokens but no hypothesis ledger or discriminating-question stage. This isolates a bounded review workflow more cleanly than comparing against a one-shot with a different budget. If A is unavailable, use the fixed collector as a separately labeled feasibility baseline; do not infer B's independent effect.

**Expected benefit / risks.** Could expose a failed assumption, especially the 3D short-input claim and 3F unknown-origin cases. It can instead rationalize a conclusion, invent a prediction, confuse absence with contradiction, or overweight a static match. Require source/runtime provenance and enforce inconclusive results when needed.

**Cost hypothesis.** Up to two extra LLM turns and one bounded lookup; input history is repeated and may exceed 2,048 tokens. Reserve output budget explicitly; record failed or too-large cases. No measured latency or accuracy exists yet.

**Accept/reject.** Shared rule, plus pre-labeled evidence-discrimination score and tests showing a counterexample or unavailable observation does not become verified causal support. Reject if false certainty rises, source-only evidence is mislabeled runtime, or success is gained merely through extra evidence/compute compared with the matched control.

## C. Runtime-evidence enrichment

**Hypothesis.** Minimal correlated runtime facts can disambiguate cases where static source and exception text cannot determine the upstream condition.

**Engineering change, if later authorized.** For **trusted fixtures only**, capture a fixed, predefined schema from a controlled test harness: test-run ID, revision, event ID, source (`harness` vs client), monotonic sequence, and explicit safe categories such as `input_shape=empty/nonempty/unknown` or a predeclared branch marker. Do not capture arbitrary arguments, user payloads, credentials or production traces. Link records with immutable IDs and clear `observed_in_fixture` scope. Select exactly which data may be included before collection, enforce byte/count/time limits, and document retention/deletion. No LLM-suggested instrumentation or arbitrary command execution. Keep current event ingestion and approval gates unchanged until separately reviewed.

**Control.** Same runtime-capable fixtures and source snapshots with the enrichment fields masked, with identical model budgets; the paired enriched arm gets only the predeclared fact. Include cases where the field is absent, ambiguous, misleading, stale or associated with another revision/request. Keep counterfactual labels outside prompts. Direct fixture test output is evidence of *that* run, not proof of a prior production event.

**Expected benefit / risks.** Could distinguish two causes that yield the same stack. Risks include false attribution across requests/revisions, missing or sampled telemetry, PII leakage, overtrust of client-supplied events and runtime instrumentation changing behavior. IDs, clocks and redaction do not automatically establish authenticity. Privacy review is a prerequisite before any extension beyond synthetic data.

**Cost hypothesis.** Fixed instrumentation and storage overhead plus at most two short records per event; unknown until measured. Record capture overhead, per-run bytes, extra tokens and wall time, missing-field rate and data-retention effects. If data or context budgets are exceeded, report unavailable and abstain; do not silently drop evidence or widen collection.

**Accept/reject.** Shared rule, plus at least two independently adjudicated ambiguous pairs where the additional field is genuinely discriminating and a mandatory cross-request/wrong-revision negative test. Reject if a recorded fixture fact is presented as a verified historical production cause or any data outside the allowlist is emitted.

## Interpretation and sequencing

A, B and C change different variables; compare each against its matched control and preregister separate analyses. A positive retrieval result cannot be generalized to B or C. None of the proposals authorizes implementation in this research-only milestone. Recommend A first; B and C remain explicitly unstarted.

## Illustrative resource planning, not measured overhead

The existing provider uses a conservative planning heuristic of approximately 3.5 characters per token; this is not a tokenizer guarantee. A's 2,000 source characters correspond to roughly **570 estimated input tokens**, before tool schema, IDs, conversation history and repeated prompts. B should cap its added hypothesis ledger at **1,200 characters** (roughly 340 heuristic tokens), in addition to any matched A-style evidence. C should cap its two extra serialized records together at **1,024 characters** (roughly 290 heuristic tokens). Actual tokenization may differ; enforce the real provider budget and fail explicitly if the evidence cannot fit.

The 3E report recorded roughly **7–15 seconds per investigation** in that particular local session, including a cold-load outlier. As a planning range only, A or B's maximum two extra calls could add roughly **14–30 seconds plus retrieval and repeated-context cost** if future calls behaved similarly; neither experiment has been run, and timeouts or different hardware can be much slower. C adds no model turn by design; its capture overhead and token-driven inference delay are unknown and must be measured. These estimates are not acceptance guarantees or production performance measurements.
