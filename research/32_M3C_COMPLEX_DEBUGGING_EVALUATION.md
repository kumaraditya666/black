# Milestone 3C — Complex debugging evaluation

Date: 2026-11-05. **PARTIALLY COMPLETE:** a small newly authored benchmark and live evaluation were completed, but this is not an independently adjudicated benchmark and does not establish general accuracy. The same operator authored, reviewed and scored the cases. No broad claim about unseen real-world repositories is justified.

## Baseline, freeze and protocol

Before benchmark creation, the full suite with Docker integrations enabled produced **91 passed, 0 skipped, one existing Starlette/httpx deprecation warning in 57.42 s**. Docker Desktop 29.9.2 Linux was reachable; `qwen3.5:4b` was installed. Existing Milestone 3B.1 working-tree changes and previous reports were preserved.

Five local synthetic cases were authored, reviewed as trusted material and frozen before any model call. Their immutable Git tree is `2221398fc77cdffaad69db6ac615e6c8be661056`, retained locally as `refs/blackbox/m3c-freeze` without moving HEAD or staging unrelated changes. This local-only ref and the Git-ignored database must be retained or explicitly exported for reproduction on another machine. The final registry and ground-truth SHA-256 values are `85876ae456572d0697e9e266505efc52ae0892692b4883e5d321e29381cb1c58` and `bcd2d2a5353199780697c9e2642a26e81cbc2b5c64863347cf6b3b184e3c73eb`, respectively. A preliminary freeze `5368a191bcaef45e70835e62310410d941a2f2b1` was revised before model evaluation to make the ambiguity case actually produce its error. A first harness invocation stopped at a metadata CRLF/LF byte mismatch before any model call; the working metadata was restored byte-for-byte from the final frozen Git tree. No fixture, label or prompt was changed in response to a model result.

`blackbox.repair.fixtures.content_pinned` verified every file against its recorded hash at the frozen revision. `data/m3c-ground-truth-audit.json` records Docker executions of each original reproduction: four failed with the specified exception and message, and the negative control passed. The event type, message and frame were transcribed from those actual trusted pytest failures; timestamps and event IDs were subsequently generated by the benchmark, not captured from a production service. The negative control deliberately supplies a false historical incident and is explicitly synthetic. The investigation collector includes the recorded event and source context, not the full pytest traceback. Each source frame resolved at the frozen revision.

The scoped harness `scripts/evaluate_m3c.py` (pre-run SHA-256 `56cea846a9eae77dc6f197795e0fd889f49d07ade29f1135d733fc8c24b21e53`) selects the frozen M3C registry in memory, keeping the existing repository and fixture eligibility checks, gates and Docker runner intact. These five specifically reviewed fixtures have the existing `approved_for_m3a` flag because the gate currently has no separate M3C registry designation; this is fixture-level test trust, not permission for arbitrary repositories. Only positive diagnosable cases received explicit labeled benchmark approval records, bound to evidence and hypothesis digests. These automatic records do **not** constitute human review or production authorization. Ambiguous and negative controls were never approved for repair.

Ollama configuration: `qwen3.5:4b`, 2048 context, 120 s provider timeout; existing prompts and schemas unchanged. Docker was required, image `sha256:5c1b730d1ae3e028494c8f6fa48a67a51d5ed2090ab0ec56b79416adb79b4fe4`; no process-jail fallback. Full investigations, eligibility checks, model usage, diffs and test outputs are in `data/m3c-live-results.json`; the associated `data/m3c-evaluation.db` is Git-ignored. Frozen benchmark source, hashes and labels are in `fixtures/repair/m3c-*` and the five `m3c_...` fixture directories.

## Ground truth and measured primary runs

| Case | Coverage and ground truth | Investigation | Patch result |
|---|---|---|---|
| `m3c_trim_total` | Multi-file, multi-function data handling: blank amount reaches `int('')`; total should ignore blanks | `LIKELY_CAUSE`, correctly identified immediate failure | `PATCH_FAILED`: model returned `None` for blank; `sum` then failed the same reproduction. No regression run |
| `m3c_window` | Boundary and algorithm: generator creates an extra partial window; downstream function raises | `INSUFFICIENT_EVIDENCE`, no repair | No patch. | `m3c_config` | Missing configuration key; default 3, preserve explicit zero | `LIKELY_CAUSE`, correctly identified missing key | `VERIFIED_IN_TEST_ENVIRONMENT`: reproduction passed after generated patch; two regression tests passed |
| `m3c_ambiguous` | `int('red')` fails; upstream provenance is deliberately absent and several sources are plausible | `INSUFFICIENT_EVIDENCE`, appropriate for attributing the upstream source | Not approved or attempted |

The configuration fix's expected default was part of the pre-specified fixture contract supplied to patch generation; it was not established by the recorded stack trace alone. The ambiguous case has a known immediate conversion failure, but its upstream cause cannot be identified from the recorded event; the label evaluates attribution, not whether the model can recognize `int('red')`. The negative case is an intentionally false client report, not a genuine observed failure.

## Scores and failure analysis

On the three cases labeled diagnosable, **2/3** identified the recorded immediate cause; one abstained. This is a single unblinded operator's assessment, not a blind causal-chain accuracy estimate. The ambiguity case abstained **1/1**. The negative control yielded **0/1 valid abstentions** and one explicit validation failure; the failed output was not preserved by the existing investigator, so its exact unsupported claim cannot be audited. Four primary investigations completed and passed existing evidence-reference checks; the three actual event messages and one ambiguous event message were separately checked against Docker failure logs. Citation ID validity does not prove semantic support, and the negative event was intentionally false. No false verified-repair claim was observed in these five cases; that is not a measured false-claim rate for a broader population.

Two proposals were generated and parsed **2/2**; both applied in-scope. One passed reproduction and regression **1/2**, while one failed reproduction **1/2**. No candidate reached regression and failed it; the failed multi-file proposal never reached regression. No rejected patch, truncated output, environment failure or security block occurred during the run. Not attempting ambiguous or negative controls reflects explicit non-approval as well as gates; it is not proof that the model would always refrain from proposing a fix.

The multi-file patch illustrates a concrete context/quality failure: returning `None` from `cleaner.parse_amount` is incompatible with the caller's `sum`; the caller file was absent from the investigation snapshot, and the patch prompt included only the allowed source file and reproduction test. This observation does not isolate whether missing context, model reasoning or both caused the bad proposal. The window snapshot includes the call to `rolling_sum` but not its definition; insufficient source context is observable, but the counterfactual effect of adding it was not measured. The config case had a directly visible source line and passed its small held-back regression suite. Thus the complex pair had 1/2 immediate diagnoses and 0/1 verified attempted patches, versus 1/1 and 1/1 for the simple config case; samples are far too small and different to establish a causal complexity effect or compare fairly with the historical 3A run.

Two investigations were repeated with the same stored incident and evidence: window abstained twice, ambiguous abstained twice. Two cases and two attempts do not characterize variability. Primary investigation latencies were 14,976, 8,589, 9,312, 7,143 and 9,153 ms in table order. Repair times were 11,460 ms (failed multi-file) and 12,664 ms (verified config); patch input/output tokens were 1300/214 and 1296/147. Investigation token counts are in the JSON; usage was not retained for the validation-failed negative investigation. An `ollama ps` snapshot during the run reported 3.1 GB, 100% GPU and 2048 context; this is a point-in-time allocation, not peak memory or energy use. Container limits were 256 MiB memory and 0.5 CPU, not measurements of actual consumption. CPU/GPU peak utilization, energy and cost were not measured.

## Recommendation

Prioritize **A: repository-wide code understanding**, beginning with bounded, revision-pinned caller/callee and cross-file context. The missing `rolling_sum` body and absent `total` caller are directly observable in these snapshots. Then test B, iterative hypothesis investigation, to obtain missing runtime evidence. This recommendation is a hypothesis grounded in two cases, not proof that adding context improves outcomes: run a pre-registered paired comparison on the same frozen tasks before claiming improvement. Maintain D's independent reproduction and regression verification; it caught the `None` patch. There is no measured basis here to choose C, a stronger model, because no model comparison was run.

## Reproducibility and limits

To repeat, preserve the local freeze ref and all Git objects, review the fixture registry and image ID, run Docker with `BLACKBOX_REPAIR_ISOLATION=docker`, configure the model and context as above, and invoke `python scripts/evaluate_m3c.py` with a fresh database/output location. The current harness deliberately refuses to overwrite its existing evidence files; archive/copy them and adjust paths in a separately documented experimental iteration. Repeats in this report were investigation-only and used `force=True`. The benchmark author and scorer were the same; no blinded second reviewer, true independent task source, known-good control patch, repository/time split, confidence interval or real-world incidents were available. `qwen3.5:4b` may have prior exposure to similar generic patterns; these locally authored fixtures were new to this evaluation but pretraining contamination cannot be excluded. Tests are narrow and not proof of semantic correctness or production safety. No arbitrary repository execution, deployment, PR or merge was enabled.

## Post-evaluation regression

The first post-benchmark full suite produced **90 passed, 1 failed, one warning**: `test_pipeline_never_mutates_the_fixture_repository` required the entire fixture directory to have an empty Git status, which the new untracked benchmark fixtures made false before the repair even ran. The test now compares the bytes and names of the fixture files before and after the repair, directly checking its intended non-mutation property even with pre-existing untracked work. No repair or investigation component was rebuilt. The final full suite, with Docker integration enabled, produced **91 passed, 0 failed, 0 skipped, one existing deprecation warning in 52.19 s**. No BLACKBOX-owned containers or pending journal remained at the final check.
